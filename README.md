Принятые решения и допущения

В задании часть требований описана, как вы и писали, написана обще. Поэтому я принял несколько решений сам и зафиксировал их здесь, чтобы поведение системы было понятным и предсказуемым

Периодическая задача хранится отдельно от обычной задачи
Я не стал добавлять настройки повторения прямо в tasks, потому что тогда одна запись одновременно означала бы и шаблон, и конкретную рабочую задачу. Это неудобно и с точки зрения модели данных, и с точки зрения дальнейшей работы со статусами

Поэтому в решении есть две сущности
Первая это шаблон периодической задачи. Он хранит правило генерации
Вторая это обычная задача, то есть конкретный экземпляр, который создается по шаблону на определенную дату и уже имеет свой собственный статус

В проекте нет cron, worker или отдельного планировщика
Из-за этого я не стал строить решение вокруг фоновой генерации. Вместо этого задачи создаются на фиксированный горизонт вперед. Также генерация повторно запускается при получении списка задач. Это позволяет обойтись без фоновых процессов и при этом держать список задач актуальным

Повторная генерация должна быть безопасной
Если один и тот же шаблон проверяется несколько раз, система не должна плодить одинаковые задачи на одну и ту же дату. Для этого добавлена защита от дублей на уровне базы данных

Для ежедневных задач правило считается от start_date
То есть если указано "каждый 3-й день", то шаг отсчитывается именно от даты начала шаблона

Для ежемесячных задач используется число месяца от 1 до 30
Такое ограничение я взял из условия задания. Если в конкретном месяце нужной даты нет, задача за этот месяц просто не создается

Для задач по четным и нечетным дням используется четность числа месяца.
Например, 2, 4, 6 это четные дни месяца
1, 3, 5 это нечетные

Для задач на конкретные даты можно передавать любые даты.
Но экземпляры создаются только в рабочем диапазоне генерации. То есть система не восстанавливает автоматически все задачи за прошлые периоды, а создает только те, которые попадают в текущий диапазон генерации

Если шаблон меняется, уже созданные задачи не переписываются
Я выбрал такое поведение, потому что оно безопаснее и проще для понимания. Изменение шаблона влияет только на будущую генерацию. Уже созданные экземпляры остаются как есть

Удаление конкретной задачи и отключение шаблона это разные действия
Если удалить или деактивировать шаблон, это не означает автоматическое удаление уже созданных задач. Они остаются в системе как отдельные рабочие записи

Timezone сохраняется и валидируется при создании шаблона. В текущей реализации он также участвует в расчете окна генерации и в вычислении дат для периодических задач. Это позволяет корректно учитывать локальную календарную дату шаблона при генерации экземпляров

Такой подход позволяет не ломать существующую модель обычных задач, аккуратно добавить периодичность и сохранить понятное поведение системы без лишней скрытой магии

API Эндпоинты
Шаблоны задач (Templates)
Метод	            URL	                    Описание
POST	            /api/v1/templates	    Создать новый шаблон
GET	                /api/v1/templates	    Получить список всех шаблонов
GET	                /api/v1/templates/{id}	Получить шаблон по ID
PUT	                /api/v1/templates/{id}	Обновить шаблон (только будущие задачи)
DELETE	            /api/v1/templates/{id}	Деактивировать шаблон (soft delete)

Задачи (Tasks)
Метод	URL	            Описание
GET	    /api/v1/tasks	Получить все задачи 


Создание ежедневного шаблона

```
curl -X POST http://localhost:8080/api/v1/templates \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Daily standup",
    "recurrence_type": "daily",
    "start_date": "2025-01-01",
    "timezone": "UTC",
    "every_n_days": 1
  }'
```

Просмотр сгенерированных задач

```
    curl http://localhost:8080/api/v1/tasks
```
